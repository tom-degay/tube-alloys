Case Study | Quantemplate Column Mapping

Mapping inconsistent schemas at scale

Turns a month of manual schema-matching into a job that runs in minutes, +75% more accurate since the 2026 upgrade.

Interaction designHuman-in-the-loop

Key points

  • Created a new mapping interaction model from users’ spreadsheet workarounds
  • Achieved 100% adoption in business-critical workflows
  • Cut mapping work from weeks to minutes for 2,000 files per month
  • 2026 upgrade delivered more reliable mappings, with 75% fewer errors in testing
Role

Research, origination of solution, detailed design, testing, revision.

Team

CTO, Product Manager, Solutions Architect, engineers.

Timeframe

1 month / 2016 v1 release
1 month / 2026 upgrade

Domain

Wholesale insurance data management.

User profiles

Data analyst: domain expert with deep knowledge of the data.
Technical skill level: competent Excel user.

Summary

Insurance companies struggle to ingest thousands of spreadsheets from different suppliers, in different structures, using different names for the same thing. Quantemplate’s mission is to solve this.

As part of this, I designed a new way to map columns across inconsistent data schemas to a common target schema, informed by usage patterns I observed in user research. The Map Column Headers feature, released in 2016, became one of Quantemplate's core capabilities, and is now a central workflow pillar for enterprises, where the average company now maps in 2,000 files per month.

In 2026 I refined the user experience to support upgraded technology behind the matching column names. Matching was now done via the semantic fingerprinting of column data using a weighting model I co-developed. Testing showed a 75% reduction in mapping errors for the same coverage.

Problem

Hundreds of schemas, no common language

Large insurance companies use hundreds of smaller partner agencies to sell policies in specific lines of business. They then underwrite those risks, and need consistent premium, claims and payments data to understand their performance, model their exposure and purchase reinsurance.

The problem is each partner agency uses a different schema for their data. A column might be called ‘Unique Market Reference’ in one dataset and ‘UMR’ in another. Now multiply that across an average of 250 fields and 2000 distinct files received per month in a typical department. That’s a huge amount of work to align the data into a format you can use.

Even worse, the schemas can change from month to month. So any solution needs to be flexible enough to allow a business analyst processing the data to instantly fix the issue. No round trips to IT or service providers.

We observed that the ingestion process was often performed manually using elaborate Excel hacks. It was slow, specialist work, the knowledge created while mapping one dataset was difficult to reuse, and the next month it all needed doing again.

Approach

Learning from the Excel workarounds

Studying dozens of Excel processes where people had manually reconciled different schemas revealed consistent patterns. The most effective approaches arranged source and target schemas vertically, using alignment across rows to show mappings. Interviews with domain experts validated the approach, but exposed a recurring pain point: constantly rearranging cells whilst keeping track of what was mapped and what remained.

Wayfinding principle: Start with people and their journeys →

Key decisions

Vertically stacked fields, aligned to a common master

There was no established product pattern that we could adopt. Instead, a concept emerged directly from the research: an interface with vertically stacked fields, across which multiple schemas could align to a common master.

The key innovation was separating mapped and unmapped fields into mutually exclusive tabs for each schema. This made it easier to spot gaps and keep track of unmapped items, whilst a progress bar indicated the completeness of each schema.

Once source schemas were mapped in, the mappings were retained. And if a new variant came in next month, it was just a couple of clicks to get it mapped in.

Processing those 2000 files a month went from taking most of the month to a job running in the background in minutes.

Implementation

Suggestions users could trust

For every unmapped field we used our matching engine to generate suggestions to map to the master schema. The next step was to automate this: allow top-ranking suggestions to be mapped at once.

I designed this as a preview mode, so users could see mapping suggestions before committing. I also added a slider, so a minimum confidence threshold could be set: incorrect mappings could be costly, so quality was more important than coverage.

These safeguards helped users trust the automation.

From column names to column contents

Whilst the interface had served our clients well, we knew the mapping algorithm itself could be improved. It just looked at the similarity of column names, and whether a pair had been mapped before. A more intelligent system would learn the contents of each column to more accurately match them to the master schema.

In 2026 we initiated a project to identify the type of data in each column, then profile the data inside it, creating a unique data fingerprint for each field.

Data semantics on the Quantemplate Help Centre →

I did a full audit of the current mapping behaviour, identified shortcomings in our approach and evaluated different paths for improvement. Together with a domain expert, I modelled different methodologies for weighting data fingerprints and prior usage.

When it came to the UI, we displayed the data types, allowing users to drill down and see detailed stats for each column. Prior mappings from other users now had avatars and recency information to build trust.

Making uncertainty visible

Improved automapping produced useful suggestions at confidence thresholds as low as 30%, compared with around 80% for the previous model. But lower-confidence mappings needed closer review.

I introduced a yellow highlight gradient to draw attention to these mappings, helping users focus their review where it mattered most. They could then inspect sample values and a data profile to judge whether a match was appropriate. Better automation needed an equally clear way to question its results.

The yellow gradient performed best among the colour options we tested, including in colour-blindness simulations and testing with a user with colour vision deficiency.

Outcome

Evaluating the new model

To evaluate the new mapping behaviour, I created four synthetic schemas based on the 250-column Lloyd’s London Market schema, which is widely used in the industry. These contained realistic data, with extensive discrepancies and lexical variation in column names, making the test more demanding than typical product usage.

In my LLM-assisted assessment across four demanding synthetic schemas, the new model achieved approximately 12% higher overall match quality and around 75% fewer serious semantic mapping errors.

That represents a fourfold reduction in errors: the new model produced roughly one error for every four produced by the old model.

Across the four schemas, only three mappings from the new model were assessed as incorrect, even with the Automap confidence threshold set to 0%. It also handled repeated and numbered fields more consistently, reducing incorrect matches between similar-looking fields with distinct meanings.
