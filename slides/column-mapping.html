07 / Reflections

Research beyond the current client base

We initially shaped parts of the workflow around clients who wanted to build a master schema from their source files. Later clients, who became the larger cohort, wanted to map to an existing standard schema. Broader market research could have surfaced this need earlier and helped us design for both workflows from the outset.

07 / Reflections

Balance stability with change

Applying a schema from a reference Data Dictionary creates an independent copy. This protects downstream operations from unexpected changes, but makes migration harder when the reference schema evolves.

I’d explore keeping a reference to the source schema while giving users control over when to adopt updates. Stable column IDs, rather than names, could help preserve downstream operations through renaming, though this would need further engineering investigation.

Tom de Gay / Column mapping
Evidence

Learning from the Excel workarounds

  • Across dozens of manual Excel processes, the most effective approaches arranged source and target fields vertically, using row alignment to show mappings.
  • Interviews with domain experts exposed the recurring difficulty: rearranging cells while keeping track of what was mapped and what remained.
Ship and learn

Completed interface

As the sole designer supporting 11 developers, I prioritised a working implementation: full interactive prototyping this data-heavy interaction would have taken comparable effort to building it. We tested internally, then refined it through customer use, adding search, populate cells and enforce schema functions. As our customer base shifted, we adapted the workflow from assembling a master schema field by field to using an existing dataset.

Making uncertainty visible

The yellow gradient performed best among the colour options we tested, including in colour-blindness simulations and testing with a user with colour vision deficiency.
Design exploration

From column names to column contents

I did a full audit of the current mapping behaviour, identified shortcomings in our approach and evaluated different paths for improvement. Together with a domain expert, I modelled different methodologies for weighting data fingerprints and prior usage.

My initial proposal prompted a different approach from a colleague. I tested both across a range of scenarios and found the other model's behaviour more logical, predictable and tunable, so we chose it over my original method.
Model evaluation

How the model was evaluated

Schema variations, reviewed with LLM assistance

What was assessed

This evaluated the matching model’s output, not the usability of the interface.

Test data

I created four schema variations to map to Lloyd’s v5.2, with discrepancies and lexical variation in column names. The accompanying data was synthetic, used only to allow Quantemplate to detect the correct data types.

Method

An LLM-assisted assessment of the mappings both models produced, carried out on 26–27 August 2026. The error counts are estimates from an LLM-assisted review of screenshots across the four schemas.

Findings

Across the four schemas, only three mappings from the new model were assessed as incorrect, even with the Automap confidence threshold set to 0%. It also handled repeated and numbered fields more consistently, reducing incorrect matches between similar-looking fields with distinct meanings.
