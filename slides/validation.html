02 / Approach

Framing

Client feedback

‘I just want to edit the failed cell’

Engineering constraint

Quantemplate is designed around rules-based transformations to data, so cell-level editing is not possible. Instead we need to make adding a rule as easy as editing a cell, and make its effect obvious.

02 / Approach

Framing

Client feedback

‘When I go back to the report view after looking at a rule, my scroll position is lost’.

Workflow analysis

The root problem isn’t just the scroll position, but having to go back to the report to navigate to the next rule.

02 / Approach

Framing

Client feedback

‘Give us an API so we can build our own validation feedback rig’

Strategic decision

Bringing the feedback workflow into Quantemplate would let business users request and manage supplier corrections without needing their IT team to build and maintain a separate system. It would also keep results and corrections connected in one auditable workflow, increasing the product’s value and supporting retention.

06 / Reflections

Adoption rates

Adoption has been uneven despite support in research. Some clients started immediately; others were reluctant to change a documented system-of-record workflow. This showed that interest in a feature doesn’t necessarily indicate readiness to adopt it.

Tom de Gay / Validation
Evidence

No easy way to fix errors in data

  • Users making ad hoc corrections in the pipeline
  • Specifically mentioned in sales process loss analysis
Evidence

Workflow was inefficient at enterprise scale

Usage had outgrown original design intent

  • User feedback like ‘I don’t care about seeing the passed rules’ and ‘When I go back to the report view after looking at a rule, my scroll position is lost’.
  • Production pipelines had hundreds of rules, we’d planned for dozens.
Design validation

Make the scope of changes obvious

Make clear which values a correction will affect

We had identified the need for multiple matching conditions, for example to apply one correction across several policy numbers. A walk-through of the design specification with a cohort of expert users confirmed it. Their feedback was that this would be much easier than wrangling Excel-style IF statements, opening corrections up to users with less technical skill.
Engineering constraint

Ordering matters

Let users review and reorder overlapping corrections

Corrections aren’t edits to cells: they’re rules, applied in sequence each time the pipeline runs. When two rules match the same value, the later one wins, so the system can’t settle the conflict on its own. Order had to become something users could see and control.
Design validation

Skip the input drill-down step

Go straight to the first failed input

I reviewed the proposed navigation changes with users in a walkthrough before implementation. No significant issues emerged, and feedback after release confirmed that the changes addressed the navigation friction they had reported.
Evidence

Choose what to share

Select the results, organisations and people

Clients told us they wanted to share their results but were concerned about sharing proprietary data. We addressed this by allowing them to select specific rules to share.
Design exploration

Submit only when ready

Prepare corrections privately, then submit

Exploring the handoff revealed a risk: sending every edit immediately could expose unfinished corrections to the receiver and trigger pipeline runs. I separated preparation from submission, giving suppliers time to check their changes before passing them back.
Design exploration

Give both parties the same measure of progress

Track only the validations that were shared

Not every failure needed correcting, so I explored tracking only checks users had started working on. But starting another check added all its failures to the total, making progress appear to drop.

I kept it simple: show how many corrections had been requested and how many were complete.
Design validation

Show before and after

Keep the original value beside the correction

I tested the prototype with a small cohort of expert users. Testing exposed two issues: users didn’t recognise the correction fields as editable, and adjacent failed columns made it difficult to tell which values belonged together.

I revised the design to give each row a clearly defined entry field, strengthen the link between original and corrected values, and refine the colour palette.
