Reflections

Adoption rates

Adoption has been uneven despite support in research. Some clients started immediately; others were reluctant to change a documented system-of-record workflow. This showed that interest in a feature doesn’t necessarily indicate readiness to adopt it.

Technical context

Technical context

Supporting corrections required rebuilding the report on a modern frontend framework. I redesigned the navigation alongside this work, retaining what worked and addressing the interactions that had become inefficient as clients added hundreds of validation rules.
Why prioritise this?

Why prioritise this?

With hundreds of validation rules in a single pipeline, every extra step between finding a failure and fixing it was repeated hundreds of times. I streamlined the route through the report by compacting navigation steps and filtering out surplus information.
More

Filter out passes

Focus on the failures and warnings

Passed validation rules are filtered out by default when viewing the report for the first time, helping users focus on their actionable task: reviewing the failures and warnings.
More

Skip the input drill-down step

Go straight to the first failed input

Knocking out the intermediate step for reviewing multiple input files takes the user straight to the data grid of the first failed input. Popups let them switch between inputs without leaving the grid, or jump to a specific input straight from the top-level view. The popup gives an indication of the number of failed rows within each input.
Design validation

Skip the input drill-down step

Go straight to the first failed input

I reviewed the proposed navigation changes with users in a walkthrough before implementation. No significant issues emerged, and feedback after release confirmed that the changes addressed the navigation friction they had reported.
More

Add direct validation rule navigation

Move between validation rules without leaving the grid

Adding buttons to navigate between validation rules within the data grid view, without returning to the report, removed three fiddly steps from the user’s workflow. Multiplied over hundreds of validation rules every month, that’s a significant time saving.

The navigator also lets users jump straight to any validation rule.

Show before and after

Keep the original value beside the correction

Corrections are shown beside the original submitted values. I chose this side-by-side layout to preserve the source data and make it clear that users are creating a correction, rather than editing the original cell.

Corrected values stand out in bright green. If no correction has been applied, the placeholder text shows the current value. This helps the user understand exactly what the output data will be.
Design validation

Show before and after

Keep the original value beside the correction

I tested the prototype with a small cohort of expert users. Testing exposed two issues: users didn’t recognise the correction fields as editable, and adjacent failed columns made it difficult to tell which values belonged together.

I revised the design to give each row a clearly defined entry field, strengthen the link between original and corrected values, and refine the colour palette.
More

Make the scope of changes obvious

Make clear which values a correction will affect

Users already understood that pipelines apply repeatable changes to data. Rather than introduce another technical concept, I kept the interface focused on their immediate decision: 'Change all matching errors' or 'Change when a condition is met'. Showing the original and corrected values side by side made the effect visible, while the popup made the scope explicit.

I added a formula bar, so users could derive a value from another column. For example, if a date is missing, take the date from another column and subtract one month. Based on what I’d observed in production pipelines, this would be a necessary addition.
Design validation

Make the scope of changes obvious

Make clear which values a correction will affect

I advocated for a simple condition builder alongside the formula bar. Formulas could express the necessary logic, but still required users to write it. Based on the technical barriers I’d observed in existing correction workflows, and my own design and product experience, I judged that formulas alone would leave the barrier too high.

The builder let users specify when a correction should apply without composing an Excel-style IF statement, while keeping formulas available for more advanced corrections. Walkthroughs with expert users confirmed the need for multiple matching conditions, and their feedback strongly supported this approach.

Preserve evidence

Keep a record of who changed what and when

Audit was important to our clients, who use Quantemplate as a system-of-record for financial reporting. To support this, I showed the original failed values alongside the corrected rows in the report. The full change history of each edit was displayed.
More

Give immediate feedback

Check the correction now, apply it on the next run

Corrections are applied to the output on the next pipeline run. Rather than wait for the run to complete to find out if a correction will now pass, after a field is completed, the system checks that the entered value will pass the validation rule, and warns if it’s still a fail.
More

Ordering matters

Let users review and reorder overlapping corrections

One of the things I discovered in testing, as part of our internal QA process, was that the order in which corrections apply is important, since one correction could overwrite a prior one. I designed an interface showing all corrections applied to any validation rule, allowing users to reorder or remove them.
Engineering constraint

Ordering matters

Let users review and reorder overlapping corrections

Corrections are applied in sequence each time the pipeline runs. When two corrections match the same value, the later one wins, so the system can’t settle the conflict on its own. Order had to become something users could see and control.
